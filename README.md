# SyncWatch

P2P 同步观影分发软件。一个人有片子，其他人不用先下载就能一起看 —— 边下边播，谁的网跟不上，全员自动停下来等他。

## 快速开始

**最简单：双击 `启动.bat`。** 首次会自动装依赖、修复 Electron、检查 mpv，然后启动。

命令行：

```bash
npm install
npm start                # 启动客户端
npm run signal           # （可选）本机跑一个信令服务器
```

需要信令服务器时，双击 `启动信令服务器.bat`。

> 启动脚本的真正逻辑在 `scripts/*.ps1` 里，`.bat` 只是个纯 ASCII 的引子。
> 这是必须的：cmd.exe 按系统 OEM 代码页解析批处理文件，把 UTF-8 中文读成乱码后
> 当命令执行，满屏报错还启动失败。PowerShell 能正确处理 UTF-8，所以逻辑放那边。
> （那几个 .ps1 存的是 UTF-8 带 BOM —— Windows PowerShell 5.1 没 BOM 会按 ANSI 读，中文照样乱。）

支持 **MP4 / MOV / M4V / MKV**，5GB 以内。

（.mov 和 .mp4 其实是同一个容器格式 ISOBMFF，box 结构完全一致 —— 同一个解析器不加改动就能读两者，ffprobe 也把它们报成同一个 demuxer。按后缀区别对待没有依据，所以一视同仁。）

### 外部依赖

本软件不自研播放器和编解码器，靠两个外部程序干活：

| 程序 | 用途 | 必需性 |
|---|---|---|
| **mpv** | 播放 + 通过 JSON IPC 被控制 | 必需 |
| **ffmpeg** | 转封装（remux） | 按需 —— 只有部分 MP4 会用到 |

```bash
winget install shinchiro.mpv Gyan.FFmpeg
# 或
scoop install mpv ffmpeg
```

装完**不用重启终端或电脑**。软件的探测不只查 PATH（winget 更新的 PATH 对已开着的进程不生效，这是「明明装了却说没找到」的头号原因），还会扫各家包管理器的落点和 winget 的 Packages 目录。装在犄角旮旯的话，用 `SYNCWATCH_MPV_PATH` / `SYNCWATCH_FFMPEG_PATH` 指过去。右上角会显示探测状态。

## 它是怎么工作的

### 边下边播靠的是「连续水位线」，不是「下载百分比」

这是整个设计的支点。接收方一开始就预分配一个和原文件等大的空文件，收到分片就按偏移写进去。播放器直接打开这个文件 —— 但它只能安全读到 **contiguousBytes**（从文件头开始连续已落盘的字节数）为止，再往后是没下到的空洞，读出来是 0，会让解码器花屏或直接崩。

所以「下载了 90%」这个数字对播放来说没有意义：只要第 2 片缺着，你一秒都播不了。界面上那条缓冲条画的就是这个 —— 绿色是可连续播放的部分，白色竖线是播放头，两者之间的距离才是你真正的余量。

### 分片调度：播放位置优先，不是 rarest-first

标准 BT 优先下最稀有的分片，为的是让副本尽快在 swarm 里扩散。代价是下载顺序基本随机，这对边下边播是致命的。

这里反过来：**当前播放位置 + 未来 30 秒**的窗口最优先，窗口外才按顺序补齐，播放位置之前的片排最后（只有回拖才用得上）。牺牲一点 swarm 健康度，换「点开就能看」。

### 全员暂停联动（与「Syncplay + 网盘」的核心差异）

每个人都在算自己的 `contiguousBytes - 播放字节位置`。低于 5 秒余量就广播 `stall`，所有人一起暂停；攒够 15 秒才解除。两个阈值拉开距离是为了滞回 —— 否则会在临界点反复横跳。

有人卡着的时候你点播放，软件会**记住你的意图但不真的播**，等最后一个人缓过来自动恢复。

### 分层

```
主进程 (Node)                     渲染进程 (Chromium)
├─ fileStore  分片/校验/水位线     ├─ peer       RTCPeerConnection 封装
├─ mpv        JSON IPC 控制        ├─ swarm      多 peer 管理 + 收发分片
├─ media      兼容性检测/转封装     ├─ scheduler  播放位置优先调度
├─ findBin    外部程序探测          ├─ syncEngine 播放同步 + 全员暂停
└─ geo        地区探测（仅告知）    └─ signaling  邀请码 / WebSocket 信令
```

分片数据流：`磁盘 →IPC→ 渲染进程 →DataChannel→ 对端 →IPC→ 磁盘`。

WebRTC 放在渲染进程是因为 Chromium 自带完整实现，不用去接 libwebrtc 的原生绑定。2MB 的 Buffer 走 IPC 有一点开销，换来的是整个 P2P 层不需要任何原生模块。

## 两种连接方式

| | 极简模式 | 信令服务器 |
|---|---|---|
| 服务器 | 完全不需要 | 只转发 SDP/ICE，不碰视频内容 |
| 操作 | 手动复制粘贴两次（邀请码 → 应答码） | 粘一次邀请码 |
| 拓扑 | 星型，所有人只连发起者 | 网状，谁都能给谁供片 |
| 邀请 | 每个人要单独走一遍 | 一个码给所有人 |

两种都不会让视频内容经过任何服务器。

## 需要你自己决定的事

### 1. 地区策略：告知 + 声明，不做拦截

原本规格要求「信令层 GeoIP 拦截 + 客户端启动校验」，现已按决定放宽为**只告知，不阻断**：

- 启动时探测所在地区，不在设计范围内就弹一条可关闭的提示，说清楚「没做适配、打洞大概率失败、需自备 TURN、这些问题不在支持范围内」。
- 首页服务条款里声明设计范围。
- **任何地区都能正常使用**，探测失败也不影响。

这么定是合理的：硬拦本来就拦不住 —— 客户端代码在用户机器上改一行就绕过，而「极简模式」压根不经过信令层，服务器想拦也够不着。真正被误伤的只有网络抖动的正常用户。

强制拦截的机制仍然保留在信令服务器里，默认关闭。有硬合规要求的部署方可以打开：

```bash
BLOCKED_COUNTRIES=CN ALLOW_UNKNOWN=0 MAXMIND_DB=./GeoLite2-Country.mmdb npm run signal
```

注意即使打开，它也只对信令模式有效 —— 极简模式绕过服务器，无法施加任何地区限制。

开发调试时 `SYNCWATCH_SKIP_GEO=1` 可跳过探测。

### 2. TURN 需要你自己提供服务器

规格说「TURN 默认开启用于兜底」。开关默认是开的，但**地址和凭据得你自己填**（设置里）—— 中继会消耗真金白银的带宽，没法内置一个公共的。不填的话，双方都在严格 NAT（CGNAT、卫星网络）后面时会连不上，界面会明确告诉用户原因。

### 3. MP4 的 moov 原子位置（规格里没提，但很关键）

规格说「仅在检测到兼容性问题时才转封装」，但没说什么算兼容性问题。实际跑下来最要命的一个是：**大部分编码器把 MP4 的 moov 索引写在文件末尾**，播放器不读到它就一帧都解不了。顺序下载的话，你得等整个文件下完才能起播 —— 边下边播直接失效。

所以 `media.js` 会解析 MP4 的顶层 box，看 moov 和 mdat 谁先出现。moov 在后面就提示转封装（`-c copy -movflags +faststart`，无损、不重编码、几十秒）。MKV 是流式容器，天生没这个问题，直接放行。

这个检测是纯 Node 实现的，不依赖 ffprobe —— 它是必查项，不能因为用户没装 ffmpeg 就跳过。

## 已验证 / 未验证

共 158 项检查，全部通过（mpv 0.41.0 + ffmpeg 8.1.2 实测）。

**端到端（两个真实 Electron 实例，1.75GB 真实影片，全程 CDP 驱动真实 UI）**

拖入 .mov → 弹出转封装确认 → 转封装 → 898 片清单 → 极简模式邀请码 → 对方粘贴 → 应答码 → 建立直连 → 清单交换 → 边下边播 → 全员暂停 → 自动解除 → 两边同步播放，位置相差 0 秒。

这一步抓出了 4 个前面 131 项检查全绿也没暴露的真 bug（见下方「端到端测试抓到的问题」）。实测吞吐 8 MB/s（本机环回），转封装 1.75GB 耗时 2.6-12s，898 片清单构建 2.0s。

**存储与分发**

- 分片切分、SHA-256 清单、fileId 可复现性
- **乱序到达时水位线的推进**：先收第 3 片水位线纹丝不动，补齐 0/1/2 后一口气跳到第 4 片
- **渐进式校验**：翻转一个 bit 的坏片当场被拒，不污染水位线；长度不符的片同样拒绝
- 全部补齐后还原文件与原文件 **SHA-256 逐字节一致**
- 断点续传（这里抓到并修了一个真 bug —— `close()` 先标记 `closed` 导致位图永远写不出去，续传静默失效）
- 位图在主进程和渲染进程两套独立实现之间往返一致
- 5GB 上限

**传输与调度**

- 2MB 分片切帧 → 乱序 + 重复投递 → 重组一致
- **两个真实 RTCPeerConnection 互联，2MB 分片经 DataChannel 传输后逐字节一致**
- 调度器：播放头优先、回拖片排最后、多 peer 负载分摊、不重复分配、只向真正持有的 peer 请求
- 信令服务器：房间隔离、`from` 字段不可伪造、重复 peerId / 未进房 / 超员的拒绝、死连接清理、端口占用的友好报错

**同步**

- 全员暂停状态机：滞回、等待名单、「卡着时点播放不真播」、最后一人恢复后自动续播
- Lamport 定序：忽略过期指令、打平时用 peerId 收敛

**媒体（实测，不再是推理）**

- **moov 检测**：ffmpeg 默认产出的 MP4，moov 确实在末尾 → 判定 remux；faststart 版本 moov 在偏移 32 → 判定可直接用。**规格里没提的这个坑是真的。**
- **转封装**：10.2MB → 10.2MB，编码仍是 h264，确认 `-c copy` 无损搬运，moov 成功挪到开头
- **mpv JSON IPC 全链路**：命名管道连接、属性观察、duration/pause/time-pos、setPause、seek、OSD、干净退出
- **`stream-pos` 可用**：有值，且 seek 到 50% 后它跟着跳到文件 51% 处 —— 可以放心当播放字节位置用，不用退化到按平均码率估算
- **mpv 打开只下了一半的稀疏 MKV**：能正常解出时长并播放水位线之内的部分；跳到空洞区时**停在水位线边界转入 `core-idle=true`，不会解码那堆 0**。水位线机制的前提成立。

**未验证**

- **真实网络下的 NAT 打洞成功率** —— 测试是本机环回，ICE 直接走 host 候选，没真正打过洞。这是唯一需要两台异地机器才能验的部分，也是剩下最大的技术风险。
- **TURN 中继路径** —— 没有 TURN 服务器可测。
- **多人（3+）同时在场** —— 逻辑支持，但只测过两个 peer。星型/网状拓扑下的转发扩散没实测。
- **接近 5GB 上限** —— 实测到 1.75GB / 16 分钟，没跑过更大的。

## 端到端测试抓到的问题

131 项零件级检查全绿，但把两个实例串起来跑真实影片时，暴露了 4 个 bug —— 全都是「各部分单独都对、组合起来不对」那一类：

1. **极简模式下一个字节都传不出去（致命）**。零服务器模式必须先用占位 id 创建 Peer（生成 offer 时还不知道对面是谁），拿到应答码才知道真实身份。而 `app.js` 换 id 时只更新了 `peers` 表，漏了 `_serving` 和 `_serveQueue` —— 发片第一步 `_serveQueue.get(peerId)` 拿到 undefined 就静默返回了。表现是「连上了、清单也收到了、界面一切正常，但进度永远 0%」。单元测试建 swarm 时直接用真实 id，从没走过改名这条路。已改为 `swarm.renamePeer()` 统一维护所有按 id 索引的表。

2. **全员暂停一旦触发就永远解不开（致命）**。stall 评估只挂在 mpv 的属性变化事件上，而 mpv 暂停后就不再推送属性变化 —— tick 断流，评估逻辑再也跑不到。死锁：缓冲不足 → 全员暂停 → mpv 静止 → 没有 tick → stall 永远不重新评估。招牌功能只会卡死不会放行。单元测试里手动连调两次 `onMpvTick()` 模拟了一个现实中不存在的世界。已增加 `onBufferProgress()` 入口，由下载进度驱动评估。

3. **观众的 mpv 在全零文件上启动，永远拿不到时长**。接收方先预分配 1.8GB 的全零稀疏文件，然后立刻拉起 mpv —— 它找不到 moov，把时长判成未知，而且之后不会重新探测。后果是连锁的：进度永远 `0:00`、前瞻窗口退化成 32MB 兜底值、stall 阈值退化成 4MB/16MB。整个流程靠 fallback 硬撑着「看起来在转」，掩盖了播放器根本没加载成功。已改为等 8MB 片头落地再启动，同步引擎则提前开工参与 stall 计算。

4. **观众的房间界面永远不显示片名**。`enterRoom()` 有个只跑一次的守卫，而观众是先连接进房、后收到清单 —— 进房时 manifest 还是 null，清单到了又被守卫挡回去。已把渲染逻辑拆成独立的 `renderFilmInfo()`。

## 明确不做（与规格一致）

内容搜索 / 资源索引、移动端、默认全量转码、承诺 100% 无服务器参与。
